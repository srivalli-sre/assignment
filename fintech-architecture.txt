Product Architecture in detail:
Our product follows a microservices architecture, where the application is divided into multiple layers.
1. Frontend Layer
This layer contains the user interfaces:
Merchant UI
Payment UI
2. Backend Layer
The backend consists of three main areas: BFF, Application, and Data layers.
A. BFF (Backend for Frontend) Layer
Acts as an intermediary between the frontend and backend services.
Aggregates data from multiple microservices and presents it in a format suitable for the UI.
It can directly communicate with the Payment Microservice to retrieve transaction status quickly.
B. Application Layer
This layer contains the core business microservices:
Ledger Microservice – Maintains accounting and transaction information, such as payment amounts and order details.
Payment Microservice – Processes payments and communicates with external banking/payment systems.
Fraud Microservice – Uses ML to identify potentially fraudulent transactions.
Notification Microservice – Handles emails, messages, and other notifications.
C. Data Layer
This layer is part of the backend and is responsible for storing and managing application data used by the microservices.

DBs used :
Ledger – MySQL for structured transaction/accounting data; Amazon S3 for receipts.
Payment – MySQL for structured payment data; Valkey for fast, in-memory/cached payment data.
Fraud Service – Neo4j for graph/relationship data; Amazon S3 for files/large datasets; Valkey for fast, in-memory/cached fraud-related data.
Notification – MongoDB for NoSQL, document-based notification data.
OpenSearch – Used for centralized log storage, indexing, searching, and analysis.

3. The Database: Why does each microservice use a different type of database? Explain why we need MySQL, Valkey, Neo4j, and MongoDB for their specific tasks.
Each microservice uses the database that best fits its data and access requirements. MySQL is used for structured transactional data, Valkey is used for high-speed in-memory access and caching, Neo4j is used for relationship-based graph data in fraud detection, and MongoDB is used for flexible document-based data. This allows each microservice to use the right technology for its specific workload.
For scalability , operational maintenance, independent delivery of MS it is good to have different database.

4. The EDA Workflow: How do these services communicate with each other when a user processes a successful payment? Trace the workflow from start to finish.
Kafka is an event-driven messaging tool or message broker that helps microservices communicate asynchronously. Each microservice listens for the events it needs. When a user initiates a payment from the Checkout UI, the request goes to the BFF and then to the Payment Service. The Payment Service calls the Fraud Service to validate the payment. If the fraud check is approved, the Payment Service sends the payment to the bank. After a successful transaction, the Payment Service publishes an event to Kafka. The Ledger Service consumes the event and stores the transaction in the database, while the Notification Service consumes the event and sends the payment details to the user.
Kafka is also used for message queue to direct logs to open search with out bottleneck
